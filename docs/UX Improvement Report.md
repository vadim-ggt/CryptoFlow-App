# UX Improvement Report

## Платформа CryptoFlow (Social Network & Real-time Messenger)

---

# 1. Введение

В данном отчёте представлена оценка удобства использования и предложения по улучшению пользовательского опыта (UX) для backend-системы `CryptoFlow`. Так как система представляет собой комплекс из REST API и WebSocket-соединений, под "пользователем" здесь понимается разработчик фронтенда, мобильных приложений или системный интегратор, который взаимодействует с программными интерфейсами.

Анализ проведён на основе атрибутов качества группы "Usability" стандарта *ISO/IEC 25010:2011 (SQuaRE)*. Также учтены лучшие практики проектирования API, которые можно соотнести с рекомендациями:

* Microsoft REST API Guidelines
* Google API Design Guide
* Спецификации протокола STOMP поверх WebSockets
* Web3 dApp Integration Guidelines

Цель улучшений — сделать API платформы CryptoFlow более:

* Понятным и логичным при первичной интеграции.
* Лёгким для отладки сложного real-time взаимодействия.
* Предсказуемым, безопасным и отказоустойчивым при высоких нагрузках (HighLoad).
* Адаптированным под стандарты Web3-экосистемы.

---

# 2. Оценка по атрибутам юзабилити ISO/IEC 25010

## 2.1 Распознаваемость соответствия

**Определение:** Степень, с которой пользователь может понять, подходит ли ПО для его нужд.

### Текущее состояние (as is)

* Наличие контроллеров `AuthController`, `UserController` и `ChatController` с эндпоинтами вида `/api/v1/...` чётко определяет предметные области: управление доступом, профили и мессенджер.
* Использование версионирования API (`v1`) с самого старта проекта сигнализирует пользователю о стабильности контракта.
* **Проблема:** Отсутствие единой интерактивной спецификации API (Swagger/OpenAPI). Разработчику клиента приходится изучать исходный код DTO и контроллеров для понимания структуры данных.

### Предлагаемые улучшения:

* Внедрение зависимости `springdoc-openapi` для автоматической генерации Swagger UI.
* Чёткое документирование WebSocket-эндпоинта (`/ws`) и каналов подписки (`/topic/chat/{id}`).

---

## 2.2 Learnability (Обучаемость)

**Определение:** Степень, с которой пользователь может научиться эффективно использовать систему.

### Текущее состояние (as is):

* Использование чётко структурированных DTO (например, `CreateMessageDto`) и мапперов снижает порог входа: клиент отправляет и получает только необходимые для бизнес-логики данные без системного "мусора".
* **Проблема:** Нестандартная аутентификация в WebSockets. Передача JWT-токена через заголовок `Authorization` в STOMP-команде `CONNECT` — это неочевидная задача для новых фронтенд-разработчиков.

### Предлагаемые улучшения:

* Создание подробной документации (в формате Markdown или в Swagger) с примерами подключения к WebSockets через библиотеки `SockJS` и `stomp.js`.

---

## 2.3 Используемость (Операбельность)

**Определение:** Степень, с которой пользователь может управлять системой и контролировать её.

### Текущее состояние (as is):

* REST API максимально автономизировано: использование `@AuthenticationPrincipal` избавляет клиента от необходимости вручную передавать свой ID — бэкенд извлекает его из JWT безопасно.
* **Проблема:** Метод получения истории сообщений выгружает всю переписку целиком. При длительных чатах это приведёт к зависанию мобильных устройств (Out of Memory) и долгому ожиданию сети.

### Предлагаемые улучшения:

* Внедрение пагинации (`Pageable`) для сообщений (Infinite Scroll), чтобы фронтенд мог запрашивать историю порциями (например, по 30 сообщений: `?page=0&size=30`).

---

## 2.4 Защита от ошибок пользователя

**Определение:** Степень, с которой система защищает пользователей от совершения ошибок.

### Текущее состояние (as is):

* Уникальный `GlobalExceptionHandler` перехватывает исключения и отдаёт стандартизированный ответ (`ErrorResponseDto`).
* Жёсткая проверка бизнес-правил: бэкенд всегда проверяет, состоит ли юзер в чате, перед выдачей данных.
* **Проблема:** Недостаточная валидация входных данных на уровне REST (например, пустые сообщения, некорректные email). Высокая нагрузка на PostgreSQL при проверке прав доступа для каждого сообщения.

### Предлагаемые улучшения:

* Внедрение `spring-boot-starter-validation` (`@Valid`, `@NotBlank`, `@Size`) в DTO-классы.
* Интеграция **Redis** для In-Memory кэширования сессий и проверок прав доступа, что защитит основную БД от перегрузки (HighLoad оптимизация).

---

## 2.5 Эстетика взаимодействия

**Определение:** Степень, с которой интерфейс (API) выглядит приятно и организованно.

### Текущее состояние (as is):

* Слой DTO отлично изолирован от Entity. Возвращается "чистый" JSON без служебных Hibernate-прокси.
* Единый формат DTO для ошибок (поля `timestamp`, `status`, `error`, `message`, `path`).

### Предлагаемые улучшения:

* Строгое использование формата ISO-8601 для всех дат (`@JsonFormat`).
* Оборачивание списковых ответов в стандартизированный объект `Page<T>` (содержащий общее число страниц и элементов) вместо простого массива `[]`.

---

## 2.6 Доступность

**Определение:** Степень, с которой система может быть использована клиентами в различных условиях.

### Текущее состояние (as is):

* WebSockets используют `SockJS`, что обеспечивает fallback-механизмы (Long Polling), если корпоративный прокси клиента блокирует прямое WS-соединение.
* **Проблема:** Отсутствие интеграции со специфичными крипто-кошельками (Web3), что сужает доступность для целевой аудитории трейдеров.

### Предлагаемые улучшения:

* Реализация Web3-авторизации и эндпоинта Connect Wallet для привязки EVM-совместимых кошельков (MetaMask, TrustWallet).

---

# 3. Уровни пользовательского опыта (UX)

## 3.1 Уровень стратегии

**Цель системы:**

* Предоставить безопасный, быстрый API для социальной сети и мессенджера трейдеров с интеграцией в Web3.

**Ожидания пользователя (фронтендера):**

* Легко подключаться к реал-тайм потоку (WebSockets), не передавать лишние системные данные и получать структурированные мета-данные (пагинация, понятные ошибки).

---

## 3.2 Уровень набора возможностей (Scope)

**Текущий набор:**

* Регистрация/Логин (JWT), CRUD профилей, создание Direct-чатов, real-time мессенджер.

**Предлагается добавить:**

* Пагинацию списков (чаты, сообщения).
* Управление групповыми чатами (`ChatType.GROUP`).
* Привязку Web3-кошельков.
* Кэширование бизнес-логики (Redis).

---

## 3.3 Уровень структуры

### Текущее состояние:

* Логичное доменное разделение: `/api/v1/auth`, `/api/v1/users`, `/api/v1/chats`.
* STOMP роутинг: `/app/chat.send` (публикация), `/topic/chat/{id}` (подписка).

### Целевое состояние:

* Расширение REST-маршрутов поддержкой query-параметров для сортировки и пагинации без изменения базовой структуры URL.

---

## 3.4 Уровень компоновки (Skeleton)

### Текущее состояние

* Стандартизированные ответы об ошибках. Использование `BaseMapper` гарантирует однотипность структур.

### Предлагаемые улучшения:

* Внедрение структуры `Page<T>`:
  `{ "content": [...], "pageable": { "pageNumber": 0, "pageSize": 30 }, "totalElements": 150, "last": false }`.

---

## 3.5 Уровень поверхности

### Текущее состояние

* Все ответы имеют MIME-тип `application/json`.
* Перехватчики (ChannelInterceptor) скрывают от клиента сложную логику STOMP-авторизации.

### Целевое состояние:

* Подключение Swagger UI в качестве визуальной "поверхности" для разработчиков, позволяющей тестировать API прямо из браузера.

---

# 4. Сравнение "До" и "После"

## Получение истории сообщений

### До улучшений

* Запрос: `GET /api/v1/chats/1/messages`
* Ответ: Монолитный массив `[{}, {}, ...]` (риск OOM на клиенте при длинных чатах).

### После улучшений

* Запрос: `GET /api/v1/chats/1/messages?page=0&size=30`
* Ответ: Структурированный JSON с порцией данных для реализации паттерна *Infinite Scroll*.

---

## Производительность (Скрытый UX)

### До улучшений

* Отправка 1 сообщения = 3-4 синхронных запроса в БД (PostgreSQL). Высокий Latency.

### После улучшений

* Отправка 1 сообщения = 0-1 запрос к PostgreSQL. Использование Proxy-объектов Hibernate и Redis-кэша. Мгновенный отклик интерфейса.

---

# 5. Соответствие рекомендациям

## Google API Design Guide

* **Простота:** Использование `@AuthenticationPrincipal` освобождает клиента от передачи дублирующей информации (ID пользователя).
* **Изоляция:** DTO-классы полностью скрывают внутреннюю схему базы данных.

## STOMP & WebSockets Best Practices

* Аутентификация выполняется через заголовок `Authorization` при `CONNECT`, а не через URL-параметры (защита от утечек токенов в логах серверов).

---

# 6. Планируемые будущие улучшения UX

1. **Архитектура (HighLoad):** Интеграция Redis для кэширования сессий и прав доступа.
2. **API:** Добавление пагинации во все эндпоинты, возвращающие коллекции.
3. **Бизнес-логика:** Полноценная реализация `ChatType.GROUP` (добавление участников, права администратора).
4. **Web3:** Эндпоинт для привязки крипто-кошелька с проверкой подписи.
5. **Документация:** Развертывание OpenAPI (Swagger).

---

# 7. Заключение

Проведённый анализ показывает, что бэкенд CryptoFlow обладает мощным и архитектурно правильным фундаментом. Слоистая структура, строгая безопасность (Spring Security + JWT) и корректная настройка STOMP-маршрутизации делают API надёжным.

Предложенные изменения направлены на решение задач масштабирования и удобства интеграции. Внедрение пагинации защитит клиенты от перегрузок, а интеграция с Redis снизит задержки (latency) до минимума, что критически важно для мессенджера. Дальнейшее развитие Web3-фичей обеспечит платформе конкурентное преимущество в нише сервисов для трейдеров.

# 9. Заключение по трассируемости

Представленная матрица трассировки демонстрирует, что все предложенные улучшения пользовательского опыта (UX) для API системы CryptoFlow имеют обоснованную связь с:

* Конкретной архитектурной или интеграционной проблемой в текущей реализации (as is).
* Чётким техническим решением, направленным на устранение этой проблемы.
* Конкретным атрибутом usability из стандарта ISO/IEC 25010:2011.

Такой подход гарантирует, что работа по улучшению API (добавление пагинации, Redis, Swagger) является структурированной, измеримой и полностью интегрированной в общий процесс развития продукта от классического бэкенда до HighLoad Web3-платформы.
