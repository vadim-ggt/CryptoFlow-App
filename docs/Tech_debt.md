## 1. Инспекция проекта на наличие технического долга

В ходе аудита кодовой базы проекта **CryptoFlow** (Spring Boot 3, PostgreSQL, JWT) была проведена инспекция по каждому из 9 классических признаков технического долга:

1. **Непонятный / нечитабельный код:** Код хорошо структурирован, однако отсутствуют JavaDoc-комментарии для сложной бизнес-логики (например, процесс генерации и валидации ключей в `JwtService`). Это повышает порог вхождения в проект.
2. **Дублирующийся код:** Уровень долга минимален. Для преобразования Entity в DTO успешно внедрена библиотека `MapStruct` (`BaseMapper`), что предотвратило появление boilerplate-кода.
3. **Отсутствие автоматизации (тестов, сборки, развёртывания):** *[Критический долг]* В проекте полностью отсутствуют модульные (Unit) и интеграционные тесты. Запуск базы данных и сборка приложения выполняются разработчиками локально вручную.
4. **Запутанная архитектура и ненужные сложные зависимости:** Архитектура (Controller -> Service -> Repository) логична. Однако в файле `application.properties` обнаружены захардкоженные креды (`11111111`) и JWT Secret. Это серьезный архитектурный дефект безопасности.
5. **Медленные/неэффективные средства:** На данный момент все прямые запросы идут в PostgreSQL. Для будущего функционала (WebSockets, обновление курсов валют) текущий подход неэффективен — требуется In-Memory хранилище (Redis), которого пока нет.
6. **Незакоммиченый код / долгоживущие ветки:** Долг отсутствует. Команда работает короткими итерациями, код регулярно вливается в `main`. Зависших веток нет.
7. **Отсутствие / несоответствие технической документации:** Отсутствует автогенерируемая спецификация OpenAPI (Swagger). Фронтенд-разработчикам приходится изучать исходный код REST-контроллеров для понимания структуры запросов.
8. **Отсутствие тестовой среды:** Разработка ведется исключительно на локальных машинах (`localhost`). Отсутствует выделенная Staging-среда и Docker-контейнеризация для изолированных тестов.
9. **Длинные циклы интеграции / отсутствие непрерывной интеграции:** CI/CD пайплайн не настроен. Отсутствуют автоматические проверки кода (линтинг, проверка Liquibase-миграций) при Push/Pull Request в репозиторий.

## 2. Области для улучшения

На основе выявленных признаков сформированы ключевые области для улучшений:

| Категория | Область для улучшения | Ожидаемый эффект |
| :--- | :--- | :--- |
| **Тестирование** | Внедрение Unit и интеграционных тестов (JUnit, Mockito) | Повышение стабильности системы, возможность безопасного рефакторинга ядра. |
| **Безопасность** | Вынос секретов в переменные окружения (.env) | Защита от утечки критических данных (DB credentials, JWT Secret) в репозиторий. |
| **Процессы** | Настройка CI пайплайна (GitHub Actions) | Устранение проблемы длинных циклов интеграции, автоматизация проверок. |
| **Документация** | Интеграция Springdoc OpenAPI (Swagger) | Автоматическая генерация интерактивной документации для фронтенда. |
| **Инфраструктура** | Контейнеризация среды (Docker Compose) | Создание единой тестовой среды, запуск БД и приложения одной командой. |

## 3. План мероприятий по устранению долга

Предлагаемый план состоит из последовательных шагов, сгруппированных по этапам в рамках стратегии внедрения общих критериев приёмки (Definition of Done).

### Этап 1. Гигиена кода и автоматизация среды (Краткосрочная цель)
1. Вынести пароли к PostgreSQL и JWT Secret из `application.properties` в системные переменные окружения.
2. Подключить библиотеку `springdoc-openapi-starter-webmvc-ui` и описать контроллеры аннотациями для генерации Swagger UI.
3. Создать файл `docker-compose.yml` в корне проекта для быстрого локального развертывания PostgreSQL 15+.

### Этап 2. Внедрение практик тестирования и CI (Среднесрочная цель)
4. Написать модульные тесты для `JwtService` (проверка логики экспирации и валидации токенов) и `AuthenticationService`.
5. Создать конфигурацию **GitHub Actions**, которая при каждом PR в `main` будет: собирать проект Maven, прогонять тесты и проверять корректность миграций Liquibase.
6. Настроить запуск интеграционных тестов Repository-слоя с использованием **Testcontainers**.

### Этап 3. Инфраструктурная эволюция
7. Интегрировать Redis через Docker Compose и настроить Spring Cache для кэширования ответов профилей пользователей.

## 4. Оценка плана мероприятий

| Мероприятие | Трудоёмкость | Риски |
| :--- | :--- | :--- |
| **1. Вынос секретов в .env** | Низкая | Ошибки запуска из-за незаполненных переменных окружения локально. |
| **2. Интеграция OpenAPI (Swagger)** | Низкая | Рисков практически нет. |
| **3. Настройка Docker Compose** | Низкая | Конфликты портов (5432) на локальных машинах. |
| **4. Покрытие кода Unit-тестами** | Средняя | Временное замедление разработки новых бизнес-фич (Time-to-market). |
| **5. Внедрение CI (GitHub Actions)** | Средняя | Сложность безопасного проброса ключей в окружение пайплайна. |
| **6. Настройка Testcontainers** | Средняя | Увеличение времени сборки (билдинга) проекта в CI. |
| **7. Подключение Redis (Кэширование)** | Высокая | Риск получения неактуальных данных (проблемы инвалидации кэша). |

## 5. Сравнение объёма долга и недоимплементированных фич

**Функциональность (Сделано):**
- Спроектирована и задокументирована (Liquibase) база данных (пользователи, чаты).
- Интегрирована надежная система безопасности (Spring Security + JWT).
- Успешно настроена слоистая архитектура REST API.

**Недоимплементированные фичи (To Be):**
- WebSockets (чаты в реальном времени).
- Интеграция с внешними Crypto API для курсов валют.
- Сложная система привязки криптокошельков.

**Объем технического долга:**
Уровень технического долга оценивается как **высокий в части инфраструктуры и автоматизации**. Код написан чисто (естественный минимум долга), однако абсолютное отсутствие автотестов и CI/CD формирует "хрупкую" систему. Объем недоимплементированных фич велик и технически сложен (WebSockets). Внедрять их в текущую архитектуру без тестов — значит гарантированно сломать уже работающую авторизацию.

## 6. Выводы и коррективы в план разработки

**Вывод:** Устранение выявленного технического долга на данном этапе является **строгой необходимостью**.
Разработка новых сложных асинхронных интеграций (WebSockets, Crypto API) в условиях отсутствия тестовой среды и автотестов приведет к деградации продукта и лавинообразному росту багов.

**Корректировки в план разработки проекта:**
1. **Приостановка продуктовой разработки:** В следующем спринте заморозить разработку новой фичи "WebSocket чаты".
2. **Фокус на тех. долг:** Выделить 1 полный спринт исключительно на выполнение **Этапа 1** и **Этапа 2** из Плана мероприятий (покрытие тестами модуля безопасности, настройка Docker Compose и GitHub Actions).
3. **Обновление Definition of Done (DoD):** Ввести жесткое правило — ни одна новая фича (User Story) не вливается в ветку `main` без покрытия Unit-тестами и без документирования в Swagger.

Только после создания этой "инфраструктурной подушки безопасности" команда вернется к реализации бизнес-фич.
